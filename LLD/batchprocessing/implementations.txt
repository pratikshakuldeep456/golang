ProcessingStep = the interface / rulebook ("must have Execute")
ValidationStep, TransformationStep, PersistenceStep = the actual workers who follow that rulebook
ChainStep = a box/node that holds one worker + a pointer to the next box, and its own Execute is really just "run my worker, 
then forward the request to the next box"

Factory decides which strategy to use. 
For example, if the batch type is ORDER, 
it gives me OrderStrategy; for PAYMENT, 
it gives me PaymentStrategy. This keeps object creation and selection out of the processor.

Strategy encapsulates batch-specific business logic.
 The BatchProcessor doesn't need to know how an order or 
 payment is processed. It just calls strategy.Process()

Chain of Responsibility handles the common processing pipeline that every item goes through
 — validation, transformation, persistence, etc. 
 Each step is independent, so I can add, remove, 
 or reorder processing steps without changing the processor.

 Factory → selects business strategy → Chain processes common steps → Strategy executes type-specific logic.

Why queue?

Suppose you receive:

1,000,000 items

If you process synchronously:

API
 │
 └── process 1M items
       │
       └── request stays open

Therefore your processing must be idempotent.

For example:

item_id = 123

DB:
processed_items
----------------
item_id UNIQUE

Then:

INSERT INTO processed_items(item_id)
VALUES (123)
ON CONFLICT DO NOTHING;

Or use an idempotency key:

batch_id + item_id
