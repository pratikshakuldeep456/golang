Functional
Select a city and see the movies showing there, with filters by language and date.
Open a movie and see its theatres and show timings.
View a show’s seat map with seat type, price and status.
Select up to 6 seats, which are locked for 10 minutes.
Confirm the booking only after payment succeeds. Otherwise the seats are released.
Get a ticket with a QR code and seat details.
Cancel a booking and get a refund if the show is more than 2 hours away.
Admins can add movies, theatres, screens and shows.


Non-functional

Thread-safe, atomic seat locking and booking, so there is no double booking.
Extensible, so new seat types, pricing rules and payment methods can be added without changing existing code.
Clean SOLID design with interfaces for storage and payment.
Expired seat locks are released automatically.
Idempotent payment and booking.

      how b tree works is-> 
      a balanced tree where each node holds many keys,
       not just one. Each node is sized to fit a disk page,
        so one node read brings in hundreds of keys.
         To find a key, we start at the root, 
         compare it with the keys in the node, 
         and follow the pointer to the right child. We repeat until we reach a leaf

         Yes, you’ve understood it correctly. In a B+ tree index, one node is stored in one page (8 KB in Postgres, 16 KB in MySQL InnoDB). Here are the steps, with one clarification.

What happens on a lookup
Read the root page from disk (it’s usually already cached in memory).
Compare within the page. The page holds many sorted keys, and the database does a binary search among them in memory, which is fast. It finds which child pointer to follow.
Read the child page and repeat until it reaches a leaf page. Each level costs one page read.
At the leaf, find your key. The leaf holds either the row itself (InnoDB’s primary key index) or a pointer to the row (Postgres, and secondary indexes in MySQL).
Fetch the row from its data page if the leaf only had a pointer.


Each node is a page that stores boundary keys and pointers to child pages.
When you search for 100, you start at the root,
 compare 100 against the boundary keys,
  and follow the pointer to the child whose range contains 100.
   You repeat this at each level until you reach a leaf.
Keys are inserted into the leaves in sorted order. When a leaf page fills up, 
it splits into two, and a separator key is pushed up to the parent.

The first request takes the lock atomically, and the second request fails with ‘seat unavailable’. The lock stays until the booking is confirmed or the TTL expires.”

irst, I try to re-acquire the seat with a conditional update: lock it for this user only if it’s still Available. If that succeeds, I confirm the booking. If someone else has taken it, I refund the payment and mark the booking Failed. To reduce this, I extend the lock when payment starts.”

“The lock lives in Redis with a TTL, so if the app server crashes, the lock expires on its own and the seats free up. Nothing is stuck. If a Pending booking row was already saved, a cleanup job marks Pending bookings older than 10 minutes as Expired. And the database unique constraint on show and seat remains the final guard.”

Confirmation is idempotent, so I retry it with the booking ID. If the seat can’t be confirmed because the lock was lost, I refund the payment.

I check that the booking belongs to the user and that the show is more than 2 hours away. Then I refund through the payment strategy, set the booking to Cancelled, release the seats back to Available with a conditional update, and publish a BookingCancelled event.”

Booking shouldn’t know how users are notified. BookingService publishes an event such as BookingConfirmed, and subscribers like email, SMS and push react. Adding a channel is a new subscriber, and a slow or failing notifier can’t break the booking.

The main weak points are: a lock expiring mid-payment (mitigated by extending the TTL and refunding), a dependency on Redis (the database constraint is the final guard), payment gateway and database drifting apart (a reconciliation job), and hot shows on release day causing contention (a per-show lock and caching the seat map).”
